# M5: LangGraph refund approval workflow

M5 follows the Day 3 LAB B workflow pattern: explicit nodes, conditional routing, a human interrupt, and a SQLite checkpoint that can resume after a restart.

## Sources and scope

M1 intake records and M2 mock refund records are separate sources. M5 never joins them and does not change either dataset or the policy corpus.

- M1 cases use one original intake record, including its supplied `ground_truth` values.
- M2 cases use one `order_ref`, inspect every linked refund row, and use the M2 calculator's `approved_amount_inr` as the amount awaiting payout.
- The M5 policy service retrieves the automated-refund cap from the `refund-authority` policy. It has M5-specific embedding and reranker settings, while querying the same Qdrant collection as M3/M4. The M5 embedding setting must match M3's indexing model or startup fails safely. The specific Refund Authorisation Matrix governs the amount cap. Category eligibility is checked only for M1 return and refund intents.

Set `SHOPSENSE_M5_POLICY_EMBEDDING_MODEL` and `SHOPSENSE_M5_RERANKER_MODEL` in `.env`. They may use the same model identifiers as earlier milestones, but M5 reads its own entries. M5 does not add a chat-model call; its workflow remains deterministic.

## Graph

```text
START → triage → policy_check → action_execution → route
                                                ├─ auto → finalize → END
                                                ├─ policy_denied → finalize → END
                                                ├─ failed → finalize → END
                                                └─ human_approval interrupt
                                                        ↓
                                                   approve/reject
                                                        ↓
                                                    finalize → END
```

`action_execution` calls the existing M2 Python functions directly. It reads and summarizes source records. It does not create, approve, process, or modify a refund record.

## Routing

For an M1 case, human approval is required when the supplied scenario has `requires_human: true`, `sentiment: "angry"`, or `claimed_amount_inr` above the policy cap.

For an M2 case, the workflow sums all `approved` refund rows for the order. An approved total above the policy cap pauses for human review. Individual source statuses remain visible and unchanged: `requested`, `approved`, `processed`, and `rejected`.

## Workflow status

- `auto_resolved`: low-risk workflow response completed using read-only data.
- `awaiting_human_approval`: graph paused at the interrupt.
- `approved_for_payout`: human approval recorded in the checkpoint; source refund rows remain unchanged.
- `rejected`: human rejection recorded in the checkpoint.
- `policy_denied`: retrieved policy explicitly denies eligibility.
- `failed`: policy retrieval or basic source validation could not complete.

## Command Prompt

```cmd
python -m shopsense.agent.cli --m5-m1-record SHOPSENSE-00000
python -m shopsense.agent.cli --m5-m2-order KW-O-000086
python -m shopsense.agent.cli --m5-resume --case-id m1:SHOPSENSE-00000 --decision approve
```

The checkpoint database defaults to `runtime/shopsense_m5.sqlite` and is ignored by Git.
